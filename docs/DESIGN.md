# Design Notes

## 1. Components and ownership

The pool owns all mutable runtime state in one actor goroutine. Public methods
submit commands over a buffered channel. The actor serializes acquire, release,
invalidate, close, configuration, waiter timeout and dial results. Query
execution deliberately happens outside the actor, but only on a connection
whose lease is present in the actor's `in_use` map.

Readers do not acquire the actor mutex. After each committed transition the
actor publishes a new immutable `PoolSnapshot` via `atomic.Pointer`. Stats and
connection-detail requests therefore see a complete version and can run
concurrently with other readers.

The module-root package `sqlitepool` is the embedding facade. It owns the
metadata store, seeds/loads config, runs recovery, and delegates to the internal
actor. Upper-layer services can therefore use the pool without importing any
`internal/` path.

Each pooled SQLite connection is represented by its own `sql.DB` limited to one
`sql.Conn`. Closing that `sql.Conn` closes the real native SQLite connection.
This is used by the loopback `conn_reset` injection and by lifecycle eviction.

## 2. State model and acquire algorithm

Runtime connection states:

- `available`: present exactly once in the ordered idle slice.
- `in_use`: present exactly once in the `in_use` map.
- `invalid`: removed from active collections; durable close/replacement fields
  remain queryable.
- `closed`: removed from active collections and retained as a tombstone in the
  current-process known-connection view.

The idle slice is FIFO by release order. Acquire work:

1. Expire any idle connection past lifetime or idle limits.
2. If waiters already exist, existing waiters have priority.
3. If no waiters and idle exists, pop the oldest idle connection and persist the
   acquisition intent.
4. If no idle and `in_use + idle + dialing < max_open`, reserve a dial slot and
   open asynchronously.
5. Otherwise enforce `max_waiters`; enqueue on success or return
   `E_POOL_EXHAUSTED` on overflow.

Waiter deadline is enforced by the actor, not by racing the caller's receive
channel. A watcher posts a timeout/cancellation command. The actor removes the
waiter and sends exactly one outcome. If assignment won first, the timeout is a
no-op; if timeout won, a later dial/release result cannot wake the waiter.

## 3. Release, wakeup and lifecycle

A release validates lifetime and idle limits. Invalid/expired connections are
closed and never reinserted into idle. If waiters exist, the released connection
is handed to the FIFO head. The observable sequence is:

- `release_handoff` event on the release;
- `acquire_wake` event on the waiter, with `woken_from_fifo: true` and wait time.

Otherwise the connection is appended to idle, and idle entries above `max_idle`
are closed from the front (oldest first). A 50 ms janitor sweeps idle connections
so max-idle/lifetime eviction is observable even without another acquire.

Successful queries update `last_used_at` through an actor touch command. The
query itself does not mutate pool collections.

## 4. Persistence schema

Metadata lives in a separate local SQLite file:

- `pool_config`: one row, monotonic version.
- `connections`: durable logical connection identity, state, timestamps, use
  count, close reason, replacement links.
- `intents`: two-phase transition records.
- `injections`: params, business code, observation, status, timestamps.
- `recovery_reports`: generated on each startup after scanning intents.

The user SQLite database and metadata database are both local files. The pure-Go
driver is pinned to a version compatible with Go 1.22.

## 5. Two-phase intent protocol

Acquire/release/invalidate use the same shape:

1. Transaction A inserts the intent as `pending` and applies the durable
   connection-state change. Commit.
2. Transaction B updates the intent to `committed`.

The durable state therefore exposes a deliberate crash window. A kill between A
and B leaves exactly enough information to roll back:

- pending acquire -> `available`;
- pending release -> `in_use`;
- pending invalidate -> `previous_state` from its payload.

Configuration changes first persist a pending intent, then atomically update the
config row and mark the intent committed with a monotonic version guard. A kill
before the second transaction leaves the old config active.

## 6. Recovery

Startup recovery runs before the new pool opens connection handles. In one
transaction it reads pending intents, applies rollback rules, marks intents
`recovered`, snapshots all connection rows before/after, and stores a recovery
report.

The report explicitly flags:

- metadata states restored: true/false;
- runtime handles preserved: false;
- exact idle queue order recoverable: false;
- facts only: true.

It includes a note that it was generated by the restarted process and is not an
exit report from the killed process. After reporting, the new process restores
available metadata rows as new live handles subject to current lifetime/idle
limits. In-use rows not recoverable as live leases remain durable facts only.

## 7. HTTP idempotency and errors

All mutation bodies are canonicalized (request ID removed, JSON map keys sorted
by encoding/json) and hashed with the route. A coordinator keyed by request ID:

- lets the first request execute;
- makes concurrent identical requests wait for the exact same status/body;
- rejects the same ID with a different digest as `E_CONFLICTING_REQUEST`.

Every failure serializes as:

```json
{"ok":false,"request_id":"...","error":{"code":"...","message":"...","context":{...}}}
```

Context always includes `business_code` and `request_id`.

## 8. Fault injection isolation

Injections are serialized by a server mutex. Each one:

- creates a durable record before acting;
- uses scoped contexts/parameters;
- cleans up internally acquired leases and waiters;
- records the resulting code and observation before responding.

The response intentionally uses the observed business error status, while the
injection record remains retrievable via `GET /v1/injections/{id}`. The E2E
suite analyzes queue residue, connection state and replacement identity after
each injection.

The debug crash-fixture route is enabled only by `-allow-debug`, on a 127.0.0.1
listener. It uses the same `PrepareAcquire` and `PrepareRelease` phase-A methods
as the actor, leaves both intents pending, and returns before the external
runner sends `SIGKILL`. This makes the crash window reproducible instead of
depending on timing.

## 9. Determinism and evidence

`cmd/e2edemo` starts the real server binary, drives HTTP, detects overlapping
lease intervals per connection, verifies FIFO wake events, checks every
injection code and persisted record, then kills and restarts the process. Its
result JSON contains raw per-step observations and pool snapshots. The checked-in
artifacts are the output of an actual run in this workspace.
