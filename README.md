在 Windows 空白工作区中，需要从零构建一个面向本地微服务测试环境的延迟队列中间件与数据处理管线。中间件维护若干延迟队列，每个队列包含多个待投递任务（任务标识、到期时刻毫秒、优先级、重试次数、资源需求），并支持并行投递调度：在全局并发上限、每轮时间预算与单任务资源预算的多重约束下，把到期任务投递给本地测试端点并依据结果执行重试或进入死信队列。投递与重试会产生状态演进，进程可能在任意时刻被强制终止，重启后必须依据持久化事实恢复队列与投递状态。用户通过本地 HTTP 接口提交任务、触发调度轮次、查询队列状态与恢复报告，结果验证工具依据持久化数据核对调度与重试的正确性。

任务环境与准备：
安装 Python 3.10 或以上版本，并安装 FastAPI、uvicorn、NumPy 与 pytest 依赖。
准备本地确定性任务样本 JSON 文件与本地 HTTP 测试端点脚本，端点可返回成功、失败或挂起响应。
确保工作区可写，SQLite 数据库文件与意图日志目录可创建。
启动本地测试端点与 FastAPI 服务，使用固定随机种子保证样本可复现。

业务要求：
1. 实现延迟任务与队列模型：任务包含标识、到期时刻（毫秒）、优先级、剩余重试次数、资源需求（整数权重）；解析本地 JSON 样本时校验到期时刻非负、优先级在 0-9 范围内、重试次数为非负整数、资源需求为正整数，解析失败返回业务码 E_TASK_INVALID 且整批不入库，同一任务标识重复提交须按幂等规则处理。
2. 定义任务状态机，至少包含 PENDING、READY、DISPATCHED、RETRY_WAITING、COMPLETED、DEAD_LETTERED 六种状态并规定合法迁移路径；非法迁移返回 E_INVALID_TRANSITION 且不得修改已持久化状态，状态迁移须同时记录迁移原因与时间戳。
3. 实现并行投递调度器：以全局并发上限、每轮时间预算与单任务资源预算三重约束推进，预算内按优先级与到期时刻升序取任务，超出并发上限的任务进入有界等待队列，队列满返回 E_QUEUE_FULL；同一任务在同一轮中不得被重复投递，同一轮内投递数不得超过并发上限。
4. 实现真实可中断的投递执行：投递到本地测试端点的请求具备独立超时，超时后必须真实关闭底层连接并返回 E_DISPATCH_TIMEOUT，不得以等待冒充超时，也不得把线程超时描述为已终止失控代码；投递成功与失败须记录端点返回码与耗时，失败时按剩余重试次数迁移至 RETRY_WAITING 或 DEAD_LETTERED。
5. 实现重试退避与预算裁决：重试等待时长依据固定退避基数与重试次数计算，退避期间任务不得被调度；当到期任务规模超出并发与时间预算可覆盖范围时，按优先级与已消耗预算给出确定性跳过次序，输出本轮被跳过任务清单及原因，低预算下必须牺牲覆盖而非违反并发上限。
6. 实现单写者调度与多读者查询的并发一致：调度轮次与状态迁移按队列单写者串行执行，多个只读查询可并发读取某一完整提交版本；同一轮次标识重复触发只执行一次、其余等待并复用结果，内容不一致返回 E_CONFLICTING_ROUND；查询不得看到任务已 DISPATCHED 而投递记录尚未写入的中间状态。
7. 使用 SQLite 持久化任务、投递记录、轮次记录与意图日志，调度前先写意图记录再提交事务；进程在投递或状态迁移中途被强制终止后重启须扫描未完成意图，把未提交投递回滚为 READY 重排或标记为已中止，恢复报告只包含已落盘事实，不得承诺强制终止后生成完整退出报告。
8. 提供本地 HTTP API 与结果验证工具：API 覆盖任务提交、触发调度轮次、查询队列状态与任务轨迹、查询恢复报告，统一失败响应为含业务码与上下文的 JSON，至少覆盖 E_TASK_INVALID、E_INVALID_TRANSITION、E_QUEUE_FULL、E_DISPATCH_TIMEOUT、E_CONFLICTING_ROUND；验证工具依据持久化投递记录核对每轮调度与重试结果并输出结构化结论。

执行约束：不使用 Docker 或其他容器环境；使用本地确定性样本验证，不访问未授权目标。按上述任务意图交付相应代码、测试或技术说明，记录实际验证结果。

验收：
使用本地样本验证延迟队列调度、超时重试、预算跳过与强制终止恢复，并核对投递记录与状态迁移。
