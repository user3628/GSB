当前是空白 Windows 工作区，需要从零构建一个面向本地微服务测试环境的消息投递语义中间件组件与可复现实验环境。组件以 SQLite 持久化消息队列、投递记录、消费者确认与消费组位点，消费者通过本地 HTTP 接口订阅并确认消息，投递语义支持至少一次与恰好一次两种模式。业务上的核心难题是并行调度与资源预算：大量队列的生产与投递需要按全局并发上限、每队列在途上限与每轮时间预算三重约束并行推进，热点队列与长尾队列并存，预算不足时必须按确定性规则降级而不能无限拖延。同时投递状态在 PENDING、DISPATCHED、ACKED、REDELIVERED、DEAD_LETTERED 之间演进，进程可能在任意时刻被强制终止，重启后必须依据持久化事实恢复投递与确认状态。所有输入来自本地固定样本与本地测试端点，不依赖外部网络。

任务环境与准备：
Windows 10 或以上，安装 Python 3.10 及以上并确保 SQLite3 可用，使用 venv 创建虚拟环境。
在虚拟环境中安装 Flask 与 requests（用于本地消费者测试端点与 HTTP 接口），版本以 pip 可安装的稳定版为准。
准备固定本地样本：若干队列及消息批次 JSON、消费者注册清单，以及可返回成功、拒绝与挂起三种行为的本地消费者测试端点脚本。
确保测试端口在回环地址上可用，所有依赖均为本地包与本地服务，不访问外部网络。

业务要求：
1. 实现消息队列与投递模型：消息包含队列名、消息标识、生产序号、体摘要、可见性超时毫秒与重试上限，消费者含消费者标识与所属消费组；同一队列内生产序号由组件单调分配且无缺口，重复入队同一消息标识须幂等并返回已有序号，不得产生第二条投递记录。
2. 定义消息与投递状态机，至少包含 PENDING、DISPATCHED、ACKED、REDELIVERED、DEAD_LETTERED 五种状态并规定合法迁移路径；非法迁移返回 E_INVALID_TRANSITION 且不修改已持久化状态；可见性超时到期后未确认消息须迁移为 REDELIVERED 并递增投递次数，重试次数超过上限时迁移为 DEAD_LETTERED。
3. 实现至少一次与恰好一次两种投递模式：至少一次模式下确认丢失或可见性超时后重投，重投不得跳过后继消息；恰好一次模式下以消息标识与消费者标识组成幂等键，重复确认返回 E_DUPLICATE_ACK 且不得重复扣减待确认计数，两种模式均须给出本轮投递与重投的统计明细。
4. 实现并行投递调度器：以全局并发上限、每队列在途上限与每轮时间预算三重参数约束执行，预算内按队列优先级与到达顺序取任务，超出并发上限的任务进入有界等待队列，队列满返回 E_QUEUE_FULL；同一消息在同一轮中不得被派发两次，同一轮内派发与确认须记录可追溯的轨迹。
5. 实现真实可中断的投递与确认执行：向本地消费者测试端点派发消息具备独立超时，超时后必须真实关闭 HTTP 客户端连接并释放其占用并发名额，返回 E_DISPATCH_TIMEOUT，不得以等待冒充超时；某次派发挂起不得阻塞其他队列的派发，也不得使整轮越过时间预算继续执行。
6. 实现预算耗尽时的确定性降级裁决：当待投递消息规模超出并发与时间预算可覆盖范围时，按队列优先级、已消耗预算与队列轮转给出确定性降级顺序，被降级消息保持 PENDING 并输出降级依据；降级后仍须保证已派发消息不被无谓中断，跳过与超时的区分须在统计中可核对。
7. 实现单写者提交与多读者查询的并发一致及幂等：投递领取、确认与状态迁移按队列单写者串行执行，多个只读查询可并发读取某一完整提交版本；同一消息同一时刻只能被一个消费者领取，并发领取仅一个成功、其余返回空结果或 E_LEASE_HELD；同一请求标识重复提交只执行一次、其余等待并复用结果。
8. 使用 SQLite 持久化消息、投递记录、确认记录与意图日志，所有写操作先写意图记录再提交事务；进程在投递或确认中途被强制终止后重启须扫描未完成意图，把未提交派发回滚为 PENDING 重排、未提交确认回滚为未确认，并输出仅基于已持久化事实的恢复报告。

执行约束：不使用 Docker 或其他容器环境；使用本地确定性样本验证，不访问未授权目标。按上述任务意图交付相应代码、测试或技术说明，记录实际验证结果。

验收：
用本地固定样本与测试消费者验证双模式投递语义、并行预算调度、确定性降级及强制终止后恢复报告。
