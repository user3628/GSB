项目从零开始，需要为一家内部 PKI 运维团队构建一个离线 TLS 握手与证书链审计工作台。团队维护多套根 CA 与中间 CA，主机侧存在大量服务端证书链，运维需要批量验证服务端证书链能否从受信根完成路径构建、握手参数（SNI、签名算法、TLS 版本、证书扩展）是否一致，并在有限 CPU 与内存预算下并行调度审计任务。工作台以本地确定性样本集为输入：每个样本包含服务端证书链（PEM）、对应的受信根集合（PEM）、以及期望的 SNI 与协议版本；审计器需要使用 Go 标准库 crypto/tls 与 crypto/x509 完成内存内握手模拟与链验证，不访问任何真实站点。由于样本量大、证书链深度不一，调度器必须在固定并发上限与总预算约束下运行，超出预算的任务被排队或按策略降级，最终输出可重复比对的 JSON 审计报告。

任务环境与准备：
安装 Go 1.22 或以上版本（Windows 安装包从 go.dev 获取），确认 go version 可执行。
仅使用 Go 标准库 crypto/tls、crypto/x509、encoding/json 与 sync，无需第三方依赖，执行 go mod init 初始化模块。
使用本地脚本或测试辅助程序生成确定性样本集：每个样本目录包含 chain.pem、roots.pem 与 meta.json（SNI、协议版本、期望结果），样本内容固定不随机。
准备异常样本目录，包含缺失中间证书、SAN 不匹配、过期与根不受信四类，供参数注入入口使用。

业务要求：
1. 实现证书链内存内握手模拟与链验证核心：对每个样本构造 tls.Config 并调用 tls.Server/Client 内存会话或等效 x509.Verify 流程，严格按给定 SNI 与协议版本执行，链路构建必须使用样本提供的根集合作为唯一信任锚，验证失败时给出稳定业务码 E_CHAIN_UNTRUSTED/E_HOSTNAME_MISMATCH/E_EXPIRED/E_EXT_KEY_USAGE 之一并保留失败证书的 Subject 与序号。
2. 实现可配置并行调度器与资源预算裁决：并发度上限、单样本 CPU 时间预算与总内存预算均为参数；调度器按样本链深度加权排队，超并发上限的任务进入等待队列而非直接拒绝，单个样本超预算时标记 E_SAMPLE_BUDGET_EXCEEDED 并释放其资源，最终报告记录每个样本的等待时长与预算消耗计量值。
3. 实现样本状态快照与检查点恢复：为每个审计样本维护带递增版本号的状态快照（待处理、验证中、已完成、失败、预算终止），每完成一个样本提交快照；运行被中断后重启可从最近快照继续，未提交样本整体重做，快照版本跳号时输出 E_SNAPSHOT_GAP 并停止依赖该快照的恢复。
4. 实现证书链拓扑一致性审计：检测链中证书的颁发者与主题是否首尾衔接、根是否在受信集合中、中间 CA 是否具备 CA:TRUE 与正确的路径长度约束，对断链、自签名非根、路径长度超限分别给出 E_CHAIN_BROKEN、E_UNTRUSTED_SELF_SIGNED、E_PATH_LEN_EXCEEDED，并输出从叶到根的完整链序摘要。
5. 实现握手参数兼容性审计：逐个样本检查 TLS 版本是否在服务端声明范围内、签名算法是否与链中证书公钥类型兼容、SNI 是否与叶证书 SAN 匹配，偏差以结构化条目记录（样本路径、字段、期望值、实际值），且同一偏差不得在不同输出位置重复计数。
6. 实现总预算耗尽时的策略裁决与结果完整性保证：当总 CPU 或内存预算不足以处理剩余全部样本时，按链深度从浅到深降级处理，被降级样本标记 E_GLOBAL_BUDGET_EXHAUSTED 但仍原样出现在报告中（不得静默丢弃），报告中的已完成、失败、降级三类计数之和必须等于样本总数。
7. 实现确定性重排与字节级可重复报告：无论调度并发度如何变化，输出的 JSON 报告按样本相对路径与失败业务码稳定排序，时间戳字段仅使用固定采样标记而非墙钟，重复运行且输入不变时报告字节级一致；并发度参数只影响调度计量字段之外不得改变结论。
8. 提供异常注入验证入口：通过参数构造四类畸形样本——缺失中间证书、叶证书 SAN 不匹配、过期证书、根不在受信集合——分别断言对应业务码、该样本未污染其他样本结论、全局计数自洽；注入不得修改源码，异常入口与正常审计共用同一调度与报告管线。

执行约束：不使用 Docker 或其他容器环境；使用本地确定性样本验证，不访问未授权目标。按上述任务意图交付相应代码、测试或技术说明，记录实际验证结果。

验收：
用本地确定性样本集运行审计，验证链验证业务码、预算裁决与报告字节级一致。
