当前是空白工作区，需要在 Windows 本地从零构建一个资源编排依赖图诊断工作台。编排对象为若干服务资源，每个资源声明标识、副本预算、依赖的父资源列表、权重与期望版本；依赖关系形成有向图，用于计算拓扑分层、影响面与编排批次。工作台需支持整份快照与只含局部改动的增量片段提交，并维护每个资源的派生结构（拓扑层级、下游影响集合、批次归属与跨资源权重一致度）。真实运维中，运维人员会不停地提交小幅增量，同时通过诊断界面在中低延迟预算下反复查询影响面与批次视图；当某个资源的关键字段变化时，其派生结构以及依赖它的聚合视图必须级联失效并原子重建，而不能让界面看到上游已更新、下游仍为旧值的中间状态。所有输入来自本地确定性 JSON 样本，通过本地 HTTP 接口操作，运行结果需可复现核对。

任务环境与准备：
确认 Windows 上已安装 Python 3.10 及以上版本，并能执行 python 与 pip 命令。
在空白工作目录创建项目并安装 fastapi、uvicorn、numpy、pytest 等依赖，版本以安装时可获取的稳定版为准。
准备本地确定性 JSON 样本：一份含资源与依赖边的整份快照、若干只含局部改动的增量片段，以及一个制造依赖环的样本，均放在项目本地的 samples 目录。
准备本地 HTTP 测试入口与启动脚本，确保服务只侦听回环地址且不依赖任何线上服务或外部账号。
预先约定 SQLite 数据库文件位置与意图日志表结构，便于中断后重启扫描未完成意图。

业务要求：
1. 实现编排快照与资源模型：每个资源含标识、副本预算（非负整数）、父资源列表、千分比整数权重与期望版本；解析本地 JSON 样本时校验标识唯一、父资源引用存在、权重落在 1 至 1000，解析失败返回业务码 E_SPEC_INVALID 且不改变已提交状态。
2. 实现整份快照加载与版本识别：快照携带单调递增版本号、生成时间与整体校验摘要，加载时校验版本单调与摘要，失败返回 E_SNAPSHOT_INVALID 且必须保持旧快照完全可用；加载成功须整体替换旧快照，禁止新旧快照的资源与依赖混合使用。
3. 实现增量片段提交：片段只含受影响资源并携带基础版本号，基础版本不是当前版本时返回 E_STALE_BASE 且不修改任何状态；同一基础版本的两个并发增量只允许一个成功，另一个必须收到 E_STALE_BASE，提交后须识别版本变化。
4. 实现拓扑分层与依赖校验：依据依赖图计算分层序号，要求所有父资源层级严格小于子资源层级；出现环时返回 E_DEPENDENCY_CYCLE 并附环上资源标识列表，同时仍须输出未被环污染的资源的层级结果与受阻资源清单。
5. 实现派生结构的级联失效与原子重建：每个资源的下游影响集合、批次归属与跨资源权重一致度须维护对资源字段与依赖边的引用关系；关键字段或依赖变化时，其全部派生结构及其下游聚合视图必须级联失效并在同一事务边界内原子重建，禁止出现部分视图已更新而依赖它的聚合仍为旧值的中间可见状态。
6. 实现低延迟诊断视图与一致性契约：影响面查询与批次视图查询须支持声明的响应时间预算，预算内返回已提交的一致性结果并标注所用快照版本；预算内无法完成时返回部分结果与明确的未完成标识，但不得返回跨版本的混合数据；同一快照版本重复查询必须得到逐位一致的层级、影响集合与批次划分结果。
7. 实现单写者提交与多读者查询的并发一致及幂等：快照提交、增量提交与级联重建按提交串行执行，多个诊断查询可并发读取某一完整提交版本；同一提交标识重复提交只执行一次、其余等待并复用结果，内容不一致返回 E_CONFLICTING_REQUEST。
8. 使用 SQLite 持久化快照版本、资源、依赖条目、派生结构与意图日志，所有写操作先写意图记录再提交事务；进程在级联重建中途被强制终止后重启须扫描未完成意图，把状态回滚到最后一个完整快照版本或将增量标记为已中止，恢复报告只包含已落盘事实，不承诺强制终止后生成完整退出报告。

执行约束：不使用 Docker 或其他容器环境；使用本地确定性样本验证，不访问未授权目标。按上述任务意图交付相应代码、测试或技术说明，记录实际验证结果。

验收：
使用本地样本验证快照与增量提交的一致性、环检测、级联重建与中断恢复，附运行结果。
