交付从新建的代码库开始，需要为多租户身份平台构建一套多因素认证（MFA）因子注册与认证可用性裁决引擎。平台内每个租户维护若干用户，用户可注册多种认证因子（TOTP、一次性恢复码、WebAuthn 公钥凭证模拟件），每条因子绑定所属租户、用户、因子类型、敏感度标签与最近一次激活标记；认证请求到来时，引擎需按租户策略从该用户已激活因子中选出满足强度的因子集合，并对每次认证尝试做可复现的挑战-应答裁决，记录因子使用次数与风控降级轨迹。引擎还需维护带版本号的因子注册快照，识别因子过期与整体替换，并在并发认证与因子重绑定下保证一人一因子的互斥占用与中断恢复。

任务环境与准备：
安装 Go 1.22 或更高版本（Windows 安装包或官方压缩包），并确认 go version 可用。
无需外部服务与网络；SQLite 通过 Go 驱动（如 modernc.org/sqlite 或 mattn/go-sqlite3）在构建时拉取，需预先 go mod tidy 完成依赖落盘。
在 Windows 本地临时目录下运行，确保当前用户对工作目录有读写权限。
样本集、挑战与伪应答源由程序内置确定性生成器产出，无需预置附件或真实账号。

业务要求：
1. 实现因子注册表与认证策略的解析与规范化：解析租户、用户、因子声明（类型、敏感度标签、状态、可重绑定标志）与策略规则（所需因子类型组合与最低强度），校验标识唯一性、因子类型受支持性与策略引用可解析性，非法输入返回 E_POLICY_MALFORMED 且不产生任何状态变更。
2. 实现挑战-应答认证裁决核心：依据用户已激活因子与策略生成确定性挑战（TOTP 时间步、恢复码索引或凭证挑战），通过本地确定性伪应答源模拟应答并判定通过或失败；TOTP 只接受配置时间窗内的步长，恢复码一次性消费后不可重用，判定结果须给出对应业务码 E_CHALLENGE_FAILED 或 E_CODE_CONSUMED 并记录所用因子。
3. 实现因子使用计数与风控降级轨迹：每个因子维护累计成功与失败次数，连续失败超过可配置阈值时将因子标记为降级并不再参与策略满足判定；降级与恢复需产生带原因与触发尝试标识的轨迹，导致某用户无可用因子时返回 E_NO_VIABLE_FACTOR 并保持用户状态一致。
4. 实现因子重绑定互斥与一致性：同一用户同一因子类型的重绑定请求须在因子粒度上互斥，任一时刻至多一个重绑定在途，成功重绑定须原子地使旧因子失效并激活新因子且不改变该用户的因子总数不变式；并发重绑定竞争时非胜者返回 E_REBIND_CONTENTION，旧因子在新因子激活前始终保持可用。
5. 实现带版本号的因子注册快照与整体替换识别：每次认证裁决、因子激活或重绑定完成后提交递增版本号快照并持久化到 SQLite，旧快照整体保留可回放；加载时校验版本链连续性，发现跳号返回 E_SNAPSHOT_VERSION 并回退到最近连续版本；内容比较须识别整体替换式版本变化，即使版本号相同而内容被整体换掉也必须判定为不一致。
6. 实现并发认证会话的资源控制：多个认证请求在独立会话中裁决，会话间状态隔离；并发度与单用户待处理认证请求数上限可配置，超并发上限的请求进入等待队列而非直接拒绝，单用户请求数超限时以 E_AUTH_BUDGET 终止该用户的新请求并保持其因子状态不被污染。
7. 实现异常注入验证链路：通过外部参数或配置文件构造因子标识缺失、恢复码重复消费、重绑定竞争、快照版本跳号与整体替换五类样本，分别断言对应业务码、受影响用户因子状态终态与快照版本变化符合预期；注入仅通过输入参数进入，不得修改源码制造验收失败。
8. 实现中断恢复与确定性诊断输出：认证或重绑定过程中进程被强制终止后重启，依赖 SQLite 已提交事务恢复因子状态、使用计数与快照版本，已提交操作不回退、未提交整体丢弃，恢复后若版本链跳号须以 E_SNAPSHOT_VERSION 报出；同时导出 JSON 诊断报告，含快照版本链、因子使用与降级轨迹、重绑定结果与业务码，按租户、用户与因子标识稳定排序且重复运行字节级一致。

执行约束：不使用 Docker 或其他容器环境；使用本地确定性样本验证，不访问未授权目标。按上述任务意图交付相应代码、测试或技术说明，记录实际验证结果。

验收：
本地确定性样本验证挑战应答裁决、重绑定互斥、快照恢复与异常注入，输出稳定 JSON 报告。
