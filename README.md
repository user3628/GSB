# 网络策略增量编译组件

交付代码位于 `cmd/`、`internal/`，一键验收脚本为 `scripts/verify.sh`。

```bash
go test ./... -count=1
./scripts/verify.sh
go run ./cmd/netpol-compiler --seed-sample
```

- 技术与 API 说明：`docs/IMPLEMENTATION.md`
- 实际验收输出：`artifacts/verification-results.txt`
- 固定种子：`internal/sample/sample.go`（seed `327`）
- SQLite 驱动：`github.com/mattn/go-sqlite3 v1.14.24`
- 默认 HTTP：`http://127.0.0.1:18080`

以下为原始任务说明。

---

本次从一份需求说明和空的模块目录开始，网络策略编译组要把策略快照的增量编译与生效裁决做成可集成的 Go 组件，供本地微服务平台的网络策略控制器使用。平台以带单调版本号的 JSON 快照维护若干命名空间下的网络策略规则：每条规则声明命名空间、规则标识、允许或拒绝、源选择器、目标选择器、端口区间、协议与优先级整数；控制器也提交只含局部规则改动的增量片段。组件需把规则编译为按选择器匹配的规则索引与端口区间合并视图，依据优先级裁决冲突并推导跨规则一致度，再按观察版本回答读方能否直接拿到编译结论、哪些必须被拒绝而不能返回陈旧索引。真实运行中同一命名空间的规则会大批量重排、端口区间相互重叠、选择器互相包含，增量片段与整份快照会被并发提交，进程也可能在编译中途被强制终止。

任务环境与准备：
Linux（WSL Ubuntu）环境，安装 Go 1.22 或以上（go version 验证）并初始化模块。
安装 SQLite 开发库（如 libsqlite3-dev），在 go.mod 引入 SQLite 驱动并固定版本以便复现。
预留本地临时目录用于 SQLite 数据文件与意图日志，运行前确保可写。
提供内置固定种子样本生成器与本地回环 HTTP 测试入口，不依赖外部网络、账号或付费资源。

业务要求：
1. 实现命名空间、网络策略规则与选择器模型：规则声明命名空间、规则标识、允许或拒绝动作、源与目标选择器（键值标签集合及 Exists 或 NotIn 谓词）、端口区间列表、协议枚举与优先级整数；解析本地确定性 JSON 样本时校验规则标识在命名空间内唯一、端口区间起止有序且不越界、优先级落在允许范围，非法输入返回 E_RULE_INVALID 并指明首个非法字段。
2. 实现带单调版本号的整份快照提交与增量片段提交：快照携带版本号、生成时间与整体校验摘要，提交时版本号不大于当前已提交版本返回 E_STALE_SNAPSHOT 且不改动已提交状态；增量片段只含受影响的规则或命名空间并携带基础版本号，基础版本不是当前提交版本时返回 E_STALE_BASE，同一基础版本的两个并发增量只允许一个成功、另一个必须收到 E_STALE_BASE。
3. 实现规则编译为选择器索引与端口区间合并视图：按命名空间把规则编译为源与目标选择器索引条目，并把端口区间按协议合并为不重叠的有序区间集合；区间重叠时必须显式声明合并规则（相邻或相交）并输出合并前后的区间数量，选择器互相包含时须保留覆盖关系而不丢失原规则标识，编译结果对同一快照版本必须逐位一致。
4. 实现优先级冲突裁决与允许拒绝叠加语义：同一选择器命中多条规则时按优先级整数从高到低裁决，允许与拒绝在同优先级下按声明次序裁决并输出命中的全部规则标识与最终动作；端口区间部分重叠时须逐端口判定而非按区间整体判定，裁决结果须附逐端口依据，同一请求在相同快照版本与相同选择器下无论规则提交顺序如何均须得到逐位一致结论。
5. 实现编译视图的级联失效与原子重建：为每个命名空间维护其规则索引、端口区间合并视图、冲突裁决结论与关联一致度对规则字段与快照版本的引用关系；某命名空间的规则新增、删除、端口区间或优先级变化时，该命名空间全部派生编译结果及依赖它的跨命名空间一致度必须级联失效并在同一事务边界内原子重建，禁止出现规则索引已更新而端口区间视图仍为旧值的中间可见状态。
6. 实现跨规则一致度的定点数值契约：由已编译规则数、冲突规则对占比与端口区间合并率按声明权重合成跨规则一致度，全程使用整数或显式定点表示并输出每步舍入方式与累计舍入误差；判断一致度是否越过声明阈值时使用带相对容差的定点比较而非裸浮点比较，容差内按命名空间标识稳定字典序打破平局，容差边界内外的结论须可区分且可复现。
7. 实现携带观察版本的陈旧读裁决与并发一致：读请求携带观察版本，若该命名空间的编译视图版本不高于观察版本则返回结论并标注所用版本，若因级联重建未完成而落后于观察版本必须返回 E_STALE_READ 并附视图版本、观察版本与落后原因；快照提交、增量提交与级联重建按版本单写者串行执行，多个读请求可并发读取某一完整提交版本，同一请求标识重复提交只执行一次、其余等待并复用结果，内容不一致返回 E_CONFLICTING_REQUEST。
8. 使用 SQLite 持久化快照版本、规则、编译视图、引用关系与意图日志，提交、编译与级联重建前先写意图记录再提交事务；进程在编译或级联重建中途被强制终止后重启须扫描未完成意图，把编译视图与引用关系回滚到最后一个完整提交版本或把增量标记为已中止，恢复报告只包含已落盘事实；同时提供本地 HTTP API 覆盖快照提交、增量提交、按观察版本查询编译视图与裁决明细、查询一致度误差说明与恢复报告，失败响应统一为含业务码与上下文的 JSON。

执行约束：不使用 Docker 或其他容器环境；使用本地确定性样本验证，不访问未授权目标。按上述任务意图交付相应代码、测试或技术说明，记录实际验证结果。

验收：
使用本地样本验证规则编译、冲突裁决、陈旧读拒绝与强制终止后的恢复一致性，并附运行结果。
