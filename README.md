在 Windows 空白工作区中，需要从零构建一个面向本地 SQLite 数据的领域数据编辑与操作应用，其核心是一套可配置的多级事务隔离与行级锁等待调度机制。应用维护若干数据表及其行版本，用户通过 HTTP API 发起带隔离级别（READ_COMMITTED、REPEATABLE_READ、SERIALIZABLE）的事务，事务内可执行行读取、行更新与保存点回滚。系统需要按隔离级别判定可见行版本，对冲突写入实施行级锁，并在并行事务争用同一行时依据资源预算（全局并发事务上限、锁等待队列容量、单次等待时限、总调度时间预算）决定授予、排队或拒绝。锁等待期间必须真实可中断，超时后释放等待槽位并回滚相应语句，不得用睡眠冒充超时。系统还需持久化事务意图与锁授予记录，进程被强制终止后依据持久化状态恢复：已提交事务保留，未提交事务回滚并释放锁，恢复报告只基于已落盘事实。所有数据来自本地确定性样本，不依赖外部数据库服务。

任务环境与准备：
安装 Python 3.11 及以上版本，并确保 pip 可用。
创建虚拟环境后安装 fastapi、uvicorn、pytest 与 httpx，版本以能离线安装的本地缓存为准。
在空白工作区建立项目目录，准备本地确定性 SQLite 样本库与并发事务脚本所需的固定参数文件。
确认本机回环端口可监听本地 HTTP 服务，运行前无需任何外部数据库或网络依赖。

业务要求：
1. 实现行版本存储与隔离级别可见性判定：每行保留版本号、提交时间戳与创建事务标识，READ_COMMITTED 事务只能看到已提交的最新版本，REPEATABLE_READ 事务在其首次读取该表时固定可见快照，SERIALIZABLE 事务在此基础上对读写集合加范围校验；同一事务内重复读取在对应级别下必须返回逐字段一致的结果，级别非法时返回 E_INVALID_ISOLATION。
2. 实现行级锁与写入冲突判定：更新某行前须取得该行排他锁，锁记录持有事务与锁模式；当另一事务持有冲突锁时，按隔离级别决定直接返回 E_WRITE_CONFLICT 还是进入等待队列；同一事务重复申请已持有锁视为可重入且不增加队列占用，锁释放必须与实际事务提交或回滚在同一事务边界内完成。
3. 实现锁等待调度与资源预算：调度器受全局并发事务上限、有界等待队列容量、单次锁等待时限与总调度时间预算四重约束；预算内按到达顺序与事务优先级授予锁，队列满返回 E_LOCK_QUEUE_FULL，等待超过单次时限返回 E_LOCK_TIMEOUT 并释放队列槽位；预算耗尽后不得再授予新锁，须输出被拒绝事务清单与拒绝原因。
4. 实现真实可中断等待与死锁处置：等待锁的事务必须通过条件通知或可中断等待原语挂起，在锁释放、超时或取消时被真实唤醒并释放底层资源，不得以固定延迟轮询冒充超时；当等待图出现环时按确定性规则选取牺牲事务并返回 E_DEADLOCK_ABORT，其余事务继续推进，牺牲事务的已执行语句必须回滚到语句前状态。
5. 实现保存点与语句级回滚的跨模块一致：事务内可设置保存点并回滚到保存点，回滚须同时撤销该点之后的行版本写入与锁申请，且不释放保存点之前已持有的锁；禁止出现行已回滚而锁仍被占用、或锁已释放而版本仍可见的中间状态；只读查询在并发写事务进行时只能看到已提交快照。
6. 实现事务意图持久化与强制终止后恢复：事务开始、锁申请、语句执行与提交均先写意图记录再改动数据，提交以单次原子事务落盘；进程被强制终止后重启须扫描未完成意图，将未提交事务对应行版本回滚并释放其全部锁，已提交事务保持不变；恢复报告只包含已持久化事实，不承诺强制终止后生成完整退出报告。
7. 实现并发控制与幂等：事务提交与锁授予按单写者串行执行，多个只读查询可并发读取已提交版本；同一事务标识重复提交只生效一次，其余请求复用同一结果；两个并发事务同时争用同一行时只允许一个进入等待队列，另一个按规则返回冲突或排队，不得出现双持有锁的可观察状态。
8. 实现统一业务错误码与可重复演示：所有失败响应为含业务码的 JSON，至少覆盖 E_INVALID_ISOLATION、E_WRITE_CONFLICT、E_LOCK_TIMEOUT、E_LOCK_QUEUE_FULL、E_DEADLOCK_ABORT、E_TX_NOT_FOUND；附本地演示脚本用固定样本并发发起三类事务并模拟一次强制终止与重启，输出各事务隔离级别下的读取结果、锁等待轨迹、被拒清单与恢复前后行版本差异，便于人工核验。

执行约束：不使用 Docker 或其他容器环境；使用本地确定性样本验证，不访问未授权目标。按上述任务意图交付相应代码、测试或技术说明，记录实际验证结果。
