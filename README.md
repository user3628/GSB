在 Windows 空白工作区中，需要从零构建一个面向本地多服务集群的容量与成本权衡组件，交付算法实现与可复现实验环境。集群由若干服务组成，每个服务声明价格单价（分/核时、分/GB时）、最小与最大资源规格及其成本预算。运维人员通过本地 HTTP 接口提交带版本号的容量快照：快照记录每个服务的副本数、每副本核数与内存、SLO 目标与预算上限；组件据此推导总成本、每服务成本占比、预算余量与跨服务加权成本指数，并判断是否违反成本约束。系统还需支持增量更新与依赖失效：当某服务的单价、规格或 SLO 变化时，依赖它的聚合成本、占比与预算裁决必须级联失效并原子重建，而非全量重算。核心难点在于增量更新与依赖失效同成本数值精度、版本一致性和强制终止恢复相互耦合：增量片段必须携带基础版本，失效传播必须在同一事务边界内完成，任何部分重建都会导致预算裁决在中断后不可复现。

任务环境与准备：
在 Windows 上安装 Python 3.11 及以上版本，并确认 python --version 与 pip --version 可用。
创建虚拟环境并安装 FastAPI、Uvicorn、NumPy 与 Pytest，版本在 requirements.txt 中固定为实际可用版本。
在项目内准备固定本地 JSON 样本：一份含至少 8 个服务的容量快照、两份只改动单个服务单价或规格的增量片段，以及一份会触发预算违例的增量片段。
预留一个本地 SQLite 数据库文件路径与意图日志目录，均由脚本创建，不依赖任何外部服务或附件。

业务要求：
1. 实现容量快照与增量片段模型：快照含单调递增版本号、生成时间、各服务的副本数、每副本核数与内存（整数）、单价（分/核时与分/GB时，定点整数）、预算上限与 SLO 目标，以及整体校验摘要；增量片段只含受影响服务并携带基础版本，基础版本非当前版本时返回 E_STALE_BASE 且不改变任何已持久化状态，校验摘要不符返回 E_SNAPSHOT_INVALID。
2. 实现成本与派生指标计算：由核数、内存、单价与副本数计算每服务成本，再计算总成本、成本占比、预算余量与跨服务加权成本指数；全程使用整数或显式定点表示（占比保留固定小数位），并输出每步舍入方式与累计舍入误差，禁止中间步骤混用浮点导致同一快照在不同计算路径下判定翻转。
3. 实现依赖失效与级联重建：为每个服务维护其对聚合成本、占比、预算余量与加权指数产物的引用关系；某服务关键字段变化时，其全部产物及依赖它的聚合产物必须级联失效并在同一事务边界内原子重建，禁止出现部分产物已更新而依赖它的预算裁决仍为旧值的中间可见状态。
4. 实现预算违例裁决与容差契约：判断总成本是否超过预算上限、成本占比是否超过服务声明上限时，使用带相对容差的定点比较而非裸浮点比较，容差内视为未违例并按稳定字典序打破平局；违例时返回 E_BUDGET_EXCEEDED 并附触发的约束名与实测值，输出中所有数值保留固定小数位。
5. 实现仅增量重建与全量重建的取舍：系统需判定增量片段是否只触达可局部重建的产物，若是则只重建受影响服务及其下游产物并输出重建范围；若触达全局产物（如加权指数的归一化基数）则走全量重建并说明原因。两条路径对同一最终快照必须给出逐位一致的成本指标与裁决，不允许无关功能充当取舍判据。
6. 实现并发控制与幂等：快照提交与重建按版本单写者串行执行，多个只读查询可并发；同一基础版本的两个并发增量仅一个成功、另一个返回 E_STALE_BASE；同一提交标识重试只执行一次、其余等待复用结果，内容不一致返回 E_CONFLICTING_COMMIT；查询只能看到某一完整提交版本。
7. 实现意图持久化与强制终止恢复：快照写入、失效传播与重建先写意图记录再提交事务；进程在级联重建中途被强制终止后重启须扫描未完成意图，把成本账本回滚到最后一个完整版本或将对应增量标记为已中止；恢复报告只基于已持久化事实，不得承诺强制终止后仍生成完整退出报告。
8. 提供统一错误响应与端到端演示脚本：所有失败响应为含业务码的 JSON，至少覆盖 E_STALE_BASE、E_SNAPSHOT_INVALID、E_BUDGET_EXCEEDED、E_CONFLICTING_COMMIT、E_LEDGER_CORRUPT；脚本用固定本地样本完成全量快照加载、仅改单服务单价的增量提交、一次触发违例的增量、一次模拟强制终止后的恢复，输出成本指标、重建范围、违例与恢复前后差异摘要。

执行约束：不使用 Docker 或其他容器环境；使用本地确定性样本验证，不访问未授权目标。按上述任务意图交付相应代码、测试或技术说明，记录实际验证结果。

验收：
用本地固定样本验证全量提交、单服务增量后的级联重建、预算违例与强制终止恢复报告一致。
