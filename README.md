当前是空白工作区，需要从零实现一个面向本地消息中间件场景的「顺序消息分区编排与事务异常注入工作台」，用于在离线环境下复现真实顺序消息与事务消息机制的核心难点。中继管理若干主题与分区，生产者以事务方式向同一分区追加消息，事务内含多条待投递记录并携带事务标识、生产者标识与逻辑序号；中继须在同一分区内严格保证消息投递顺序与事务原子性：一个事务的消息要么按序全部可见，要么全部不可见，中途失败不得让后续事务越过未完成事务插队。消费端按分区拉取消息并确认位点，未确认消息可在超时后按原序重投。工作台还需支持按注入点与触发计数精确复现异常，从而在本地验证各类失败路径的恢复行为。由于投递顺序依赖持久化状态，进程重启后的恢复必须依据已提交事务、分区位点与顺序栅栏判定，而不是扫描全量日志重放。

任务环境与准备：
安装 Python 3.11 及以上版本，并在工作区创建虚拟环境。
通过 pip 安装 fastapi、uvicorn、pytest 与 httpx，版本以本地可用为准，全程离线可运行。
确认 SQLite 由 Python 标准库 sqlite3 提供，无需额外服务；准备本地样本目录用于存放主题、事务与注入配置 JSON。
确认 Windows 上可正常启动本地 HTTP 服务并访问 127.0.0.1，测试过程不依赖外网与外部中间件。

业务要求：
1. 实现主题、分区与事务消息的声明模型及解析校验：主题含名称、分区数与保留策略，事务消息含事务标识、生产者标识、分区键、逻辑序号、消息负载与内容摘要。须校验分区键散列能在分区数内稳定映射、同一生产者同一分区的逻辑序号不得回退、事务内消息条数不超过配置上限，非法输入返回固定业务码 E_BAD_REQUEST 且不得写入任何状态。
2. 实现分区内的顺序栅栏与事务原子可见性：未提交事务的消息须暂存不可见，同一分区内后到事务不得越过先到但未完成的事务被消费；事务提交须在单事务中同时释放其全部消息并使分区可消费位点推进，回滚须整体丢弃且不改变可消费位点。分区内可见消息的逻辑序号序列必须严格递增且无空洞，违反时返回 E_ORDER_VIOLATION。
3. 实现消费拉取、确认与超时重投的顺序语义：消费者按分区与逻辑序号顺序拉取已提交消息，确认须按位点递增提交，跳位确认须拒绝并返回 E_CONFIRM_GAP；未确认消息在确认超时后须按原逻辑序号顺序重投且不得插入新提交事务的消息之前。同一消息重复投递须保持相同内容摘要，重投次数超上限时返回 E_DELIVERY_EXHAUSTED 并登记死信。
4. 实现可复现异常注入机制：注入配置来自请求参数或配置文件，按注入点名称（append、fence、commit、fetch、confirm）与触发计数精确定位，仅在指定注入点第 N 次被调用时抛出指定异常，其余调用正常执行；注入须可通过关闭配置完全消除，同一输入在注入关闭时结果必须一致。注入计数须持久化并可在查询接口中观察当前计数水位。
5. 实现异常链路映射与失败原子性：追加失败、栅栏拒绝、提交失败、拉取失败、确认失败与注入异常须映射为互不重叠的固定业务码集合，注入异常统一映射为 E_INJECTED 并携带注入点与计数；任一阶段失败后不得留下部分写入的事务记录、可见的半事务消息或错误的位点推进，失败后关闭注入以相同输入重试须成功且结果与从未失败过时一致。
6. 实现 SQLite 持久化与进程重启恢复：事务状态、分区可消费位点、确认位点、顺序栅栏、重投计数与注入计数须在提交点以单事务写入，事务提交后才对查询可见；重启后须把中断时处于提交中的事务判定为不可见并清理其暂存消息，恢复后同一分区继续追加的事务其可消费顺序必须与未中断运行逐条一致，不得出现序号回退。
7. 实现并发生产与消费下的分区一致性：同一分区的追加与栅栏判定须串行化到分区边界内，不同分区可并行推进；并发事务提交时须只允许栅栏头部事务推进，其余事务等待且锁等待须有真实超时并返回 E_CONTENTION_TIMEOUT。并发确认与超时重投不得让同一消息同时被标记为已确认与已重投。
8. 提供本地 HTTP 接口与可重复测试：通过本地 HTTP 提供创建主题、追加事务消息、提交或回滚事务、拉取消息、确认消息、查询分区状态与死信、查询注入计数的接口，错误统一以固定业务码在 JSON 中返回。内置固定随机种子的生产者与消费者桩，pytest 用例须在 Windows 离线覆盖顺序栅栏、事务原子性、跳位确认拒绝、注入各注入点、重启恢复与并发争用。
