在 Windows 空白工作区中，需要从零构建一个面向本地多服务测试环境的配置中心热更新中间件，交付数据处理管线与结果验证工具。配置中心维护若干客户端订阅的配置项（数值型参数、比例、阈值），配置以带版本号的快照提交，热更新时向本地客户端测试端点推送增量并等待确认。客户端依据最新配置执行确定性数据计算管线（对固定本地样本做加权求和、归一化与阈值判定），并回传计算结果。难点在于交互延迟与计算结果一致性：推送延迟导致不同客户端在不同时刻拾取配置版本，同一批次计算结果可能混用不同版本参数；迟到确认与重复推送会使已应用版本被覆盖；进程被强制终止后恢复必须依据持久化事实。

任务环境与准备：
安装 Python 3.11 或以上版本，创建虚拟环境并安装 fastapi、uvicorn、numpy、pytest、httpx。
初始化空白工作区，创建项目目录与 SQLite 数据库文件路径，数据库文件由程序在首次启动时创建。
准备本地确定性样本张量生成配置（固定随机种子与样本规模参数）作为计算管线输入，不依赖外部数据集。
启动本地客户端测试端点服务（HTTP），用于接收配置推送与返回确认，所有端点绑定回环地址。
运行演示脚本前确保本地端口未被占用，脚本自行拉起服务与测试端点并完成一次端到端热更新流程。

业务要求：
1. 实现配置快照与订阅模型：快照包含单调递增版本号、生成时间、配置项集合与校验摘要；客户端声明其依赖的配置键集合与本地测试端点地址。提交快照时若版本号不大于当前已提交版本则返回 E_STALE_SNAPSHOT；若校验摘要不一致返回 E_SNAPSHOT_INVALID，且不得改变任何已提交状态。
2. 实现配置推送与确认状态机，至少包含 PENDING、PUSHED、ACKED、APPLIED、ABORTED 五种状态并规定合法迁移路径；非法迁移返回 E_INVALID_TRANSITION 且不修改已持久化状态；确认迟到或重复确认须按确定规则处理，不得把已 APPLIED 的版本回退为旧版本。
3. 实现交互延迟约束下的热更新推送：每个客户端推送具备独立超时，超时后必须真实关闭与该本地测试端点的底层连接并返回 E_PUSH_TIMEOUT，不得以等待冒充超时；推送延迟超过配置窗口时按降级策略仅对已确认客户端推进版本，并输出本轮未推进客户端清单与原因。
4. 实现使用固定随机种子生成样本张量的确定性计算管线：输入样本规模、配置版本与配置参数必须唯一决定计算结果；管线按客户端拾取的配置版本执行加权求和、归一化与阈值判定，并回传结果摘要。同一配置版本与样本重复执行必须逐位一致，禁止依赖隐式全局随机状态。
5. 实现计算结果一致性校验：当同一批次中不同客户端因拾取版本不同而得到不同结果时，须输出不一致明细，包含客户端标识、其拾取版本、结果摘要与差异字段；校验工具依据快照版本与客户端确认记录判定哪些结果可并入最终结论，禁止混入未确认版本的结果。
6. 实现重复推送与迟到确认的幂等与版本保护：同一客户端同一配置版本的重复推送只生效一次，内容不一致返回 E_CONFLICTING_PUSH；迟到确认若对应版本已被更新版本取代则计入历史并返回 E_STALE_ACK，不得覆盖新版本的应用状态。
7. 实现并发控制与可见性：配置提交与推送推进按版本单写者串行执行，多个查询可并发读取已提交的客户端状态与计算结果；同一版本重复触发推送只执行一次、其余等待并复用结果；查询不得看到客户端已 ACKED 而配置版本仍为旧值的中间状态，并须明确读写事务边界。
8. 使用 SQLite 持久化快照、推送记录、确认记录与计算结果摘要，写操作先落意图记录再提交事务；进程在推送或结果汇总中途被强制终止后重启须扫描未完成意图，将客户端与批次恢复到最后一个完整版本或标记为已中止，并输出仅基于已持久化事实的恢复报告；提供本地测试端点与可重复演示脚本，输出每轮推送、确认、结果一致性与恢复结论。

执行约束：不使用 Docker 或其他容器环境；使用本地确定性样本验证，不访问未授权目标。按上述任务意图交付相应代码、测试或技术说明，记录实际验证结果。

验收：
使用本地样本验证热更新推送、计算结果一致性与异常恢复，附运行结果。
