在 Windows 空白工作区中，需要从零构建一个面向本地多组件协同平台的配置分发与状态协调管线。平台包含配置仓库、分发协调器、若干本地组件端点（以本地 HTTP 测试服务形式模拟）与结果验证工具。配置以带版本号的 JSON 快照提交，协调器依据组件声明计算受影响的组件集合，按阶段把配置推送到各组件端点，并追踪每个组件在 PENDING、DISPATCHED、APPLIED、FAILED、ROLLED_BACK 之间的状态演进。难点在于状态演进与恢复一致性：推送过程中可能有组件失败、超时或进程被强制终止，协调器必须在持久化事实基础上把整体状态收敛到一致结论，不能出现部分组件显示已应用而快照版本不一致的中间状态。所有输入来自本地确定性样本，不依赖外部账号或线上站点。

任务环境与准备：
安装 Python 3.11 及以上版本，确认 python 与 pytest 可在命令行直接调用。
创建空白工作目录并在其中初始化项目结构，SQLite 使用标准库 sqlite3，无需额外数据库服务。
准备固定本地样本文件：配置快照 JSON、组件声明 JSON 与测试端点响应脚本，全部置于项目内且内容确定。
本地测试组件端点以进程内 HTTP 服务或本地回环端口启动，不依赖外部网络与容器环境。

业务要求：
1. 实现配置快照与组件声明模型：快照包含版本号、生成时间、配置项集合与校验摘要；组件声明包含组件标识、依赖的配置键、期望配置版本与本地端点地址。提交快照时若版本号不大于当前已提交版本则返回业务码 E_STALE_SNAPSHOT 且不改变任何状态，若校验摘要不匹配或必填字段缺失则返回 E_INVALID_SNAPSHOT。
2. 实现影响分析与分发计划生成：依据组件声明中的配置键依赖，计算受新快照影响的组件集合以及需要连带重新分发的下游依赖组件，生成按依赖拓扑排序的分发计划；当依赖出现环时返回业务码 E_DEPENDENCY_CYCLE 并给出涉及组件，计划生成结果需与快照版本绑定且可重复生成一致计划。
3. 实现组件状态机，至少包含 PENDING、DISPATCHED、APPLIED、FAILED、ROLLED_BACK 五种状态并规定合法迁移路径；非法迁移返回 E_INVALID_TRANSITION 且不修改持久化状态；每个组件的状态记录必须携带其依据的快照版本，禁止出现状态与版本不匹配的可见记录。
4. 实现向本地组件端点推送配置：推送请求携带快照版本、配置项与幂等请求标识，端点以本地 HTTP 测试服务实现，可返回成功、业务拒绝或延时响应；协调器需区分推送被拒绝、连接失败与超时，超时须真实关闭连接并释放资源，不得以等待冒充已终止，各情形返回互不相同的业务码。
5. 实现失败处置与整体收敛：当某组件推送失败时，依据配置的失败策略选择继续其余组件并最终标记整体为部分应用，或触发对已应用组件的回滚；无论哪种策略，必须保证同一快照版本下所有已应用组件最终处于一致结论，部分应用与回滚不可在同一次分发中混用而未标记。
6. 实现并发控制与可见性：分发执行按快照版本单写者串行，多个只读查询可并发；同一快照重复触发分发时仅一个实际执行、其余等待复用结果；查询不得看到某组件已标记 APPLIED 而其快照版本仍为旧的中间状态，分发中新增的快照提交须排队等待当前分发结束。
7. 使用 SQLite 持久化快照、分发计划与组件状态，写操作先落意图记录再提交；进程在推送过程中被强制终止后重启必须扫描未完成意图，将未完成分发标记为已中止并按持久化事实回滚或重新排队，恢复报告只包含已持久化事实，不得承诺强制终止后仍生成完整退出报告。
8. 提供结果验证工具与端到端演示脚本：验证工具读取持久化状态，检查组件状态与快照版本一致性、依赖闭合与状态迁移合法性并输出结构化验证结论；脚本使用固定本地样本与本地测试端点完成一次全量分发、一次含失败组件的分发、一次并发重复触发与一次强制终止后恢复，输出每次的组件状态轨迹与验证结论。

执行约束：不使用 Docker 或其他容器环境；使用本地确定性样本验证，不访问未授权目标。按上述任务意图交付相应代码、测试或技术说明，记录实际验证结果。

验收：
使用本地样本与测试端点完成分发、失败处置、并发与强制终止恢复，验证工具输出状态与版本一致结论。
