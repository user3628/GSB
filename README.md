当前是空白工作区，需要从零实现一个面向本地分库分表中间件场景的「路由元数据增量刷新与依赖失效引擎」。引擎维护逻辑表到物理分片的路由规则：逻辑表声明分片键、分片算法（取模、范围、哈希取模）、物理库数、每库表数与分片映射表；同时维护绑定表关系、广播表标记与全局索引到逻辑表的引用关系。客户端以逻辑表名加路由键提交路由解析请求，引擎返回目标物理库表；运维侧提交元数据补丁（新增逻辑表、调整分片算法参数、变更绑定关系、下线物理分片），引擎需沿依赖图计算失效闭包，只重建受影响逻辑表的物理路由表快照，并让依赖该路由的全局索引与缓存条目级联失效。路由表版本、依赖图与失效事件需持久化到 SQLite 以支持进程重启后的恢复，整个过程通过本地 HTTP 接口驱动。

任务环境与准备：
安装 Python 3.11 及以上版本，并安装 FastAPI、uvicorn、pytest 与 httpx 依赖。
准备本地样本目录，包含逻辑表、绑定表、广播表与全局索引的元数据 JSON 及若干补丁文件。
确保可在 Windows 上本地启动 HTTP 服务并离线运行 pytest，不依赖外网与真实数据库。

业务要求：
1. 实现路由元数据模型与补丁解析：逻辑表声明分片键、分片算法及参数、物理库数与每库表数，绑定表关系与广播表标记单独声明；补丁以 JSON 操作序列描述新增、修改与下线操作，解析时须检测目标实体不存在、算法参数缺失、分片键不属于表列等情形并返回 E_BAD_PATCH，不得进入后续计算。
2. 实现基于依赖图的路由失效闭包计算：元数据变更后从变更实体出发计算失效闭包，必须包含直接变更的逻辑表与所有依赖它的绑定表、全局索引与缓存条目，不得包含无关逻辑表；分片算法参数变化只使该逻辑表及其绑定表失效，改变绑定关系只使参与绑定的成员失效，诊断报告须列出每个失效实体的直接触发变更与传播路径。
3. 实现局部物理路由表重建与全量等价校验：只对失效闭包内逻辑表重新生成路由表，未失效逻辑表复用上一版本路由片段，重建后的完整路由表须与从零全量重建在规范化序列化后逐字段等价；重建中途失败须回退到上一版本并返回 E_REBUILD_FAILED，不得留下部分更新。
4. 实现路由版本的单调推进与快照整体替换：每次成功应用补丁生成递增版本号，快照元数据文件须携带版本号并在整体替换前先写临时文件校验摘要后原子替换；启动时若发现版本号未变化但内容摘要变化须判定为损坏并返回 E_SNAPSHOT_CORRUPT，替换前旧快照保持可读。
5. 实现并发补丁提交与快照生成的互斥：同一逻辑表的快照生成期间到达的新补丁须等待当前快照完成后再计算失效闭包，避免基于陈旧依赖图生成快照；并发补丁提交须串行化版本号分配，保证版本号严格递增且无空洞；锁等待须按真实单调时钟超时并返回 E_CONTENTION_TIMEOUT。
6. 实现路由解析与缓存失效的联动：路由解析请求须在快照一致性边界内读取路由表并返回物理库表定位与所依据的路由版本；缓存条目绑定其生成时的路由版本，当依赖的逻辑表失效闭包被触发时对应缓存条目必须失效，缓存命中与未命中的解析结果须一致，失效后不得返回陈旧物理定位。
7. 实现进程重启后的状态恢复与失效补算：版本链、依赖图、缓存条目与未完成的失效事件须在提交点以单事务写入 SQLite；重启后须把中断时处于重建中的逻辑表回退到上一版本，并对已变更但未触发级联失效的路由补算失效，恢复后的路由解析结果须与重启前最后一次已提交快照一致。
8. 提供本地 HTTP 接口与可重复测试：通过本地 HTTP 提供提交补丁、查询版本链、查询依赖图、查询路由解析、查看失效闭包诊断报告与强制全量重建对比的接口，错误统一以固定业务码在 JSON 中返回；使用至少四个逻辑表、含绑定表与全局索引的本地样本，pytest 用例须在 Windows 离线覆盖非法补丁拒绝、失效范围正确、局部与全量等价、并发互斥与重启恢复。
