新接手的分库分表中间件需求尚未开工，工作区为空，需要在本机从零实现一套面向本地多逻辑库的领域数据编辑与操作应用。集群由若干逻辑库组成，每个逻辑库包含若干分表，路由规则以带版本号的 JSON 快照描述分片键、取模或范围分片算法、逻辑表到物理表的映射、分片区间与权重，运维人员通过本地 HTTP 接口提交整份快照或只含受影响逻辑表的增量片段，客户端携带路由版本提交查询并期望在版本被替换时得到明确裁决而不是陈旧结果。真实场景中逻辑表会新增、分片区间会被重划、部分逻辑表会被合并到同一物理表，路由快照替换期间既有查询仍在执行，因此必须同时处理增量变更的基础版本校验、版本绑定读取、派生路由缓存的级联失效与进程强制终止后的恢复，本应用交付可操作的领域数据编辑界面与可复现的验证脚本。

任务环境与准备：
Windows 本机安装 Go 1.22 或以上，确认 go version 可用，并设置可写的模块缓存目录。
无需外部数据库服务，SQLite 以嵌入方式使用（如 modernc.org/sqlite 纯 Go 驱动），依赖通过 go mod tidy 拉取，联网不可用时预先放入本地模块缓存。
在空白工作区初始化 Go 模块，准备固定种子的本地 JSON 路由快照样本与增量片段样本，样本由程序内置生成器产出，不依赖真实集群。
提供本地 HTTP 监听端口用于演示与验证，端口从配置读取，避免与已有服务冲突。

业务要求：
1. 实现路由快照与逻辑表模型：快照携带单调递增版本号、生成时间、分片键、分片算法参数、逻辑表到物理表映射、分片区间与整体校验摘要；解析本地 JSON 样本时校验逻辑表标识唯一、物理表映射存在、区间下界不大于上界且相邻区间不重叠，解析失败或摘要不一致返回业务码 E_SNAPSHOT_INVALID 且必须保持旧快照完全可用。
2. 实现增量片段提交与基础版本校验：增量片段只含受影响的逻辑表或分片区间并携带基础版本号，基础版本不是当前已提交版本时返回 E_STALE_BASE 且不改变任何已提交状态；同一基础版本的两个并发增量只允许一个成功，另一个必须收到 E_STALE_BASE，且整批增量在同一事务边界内全部生效或全部不生效。
3. 实现路由计算与分片区间边界语义：对等值、范围与 IN 列表查询分别计算目标物理表集合，取模与哈希算法须使用固定种子与确定性实现，范围查询须显式声明区间端点包含关系并处理跨分片区间与空区间；结果按物理表标识稳定排序，同一请求与同一路由版本重复计算必须逐项一致。
4. 实现版本绑定读取与陈旧读裁决：查询请求携带观察版本，若该逻辑表的路由缓存版本不高于观察版本则返回结果并标注所用版本；若因增量传播未完成而落后于观察版本必须返回 E_STALE_READ 并附缓存版本、观察版本与触发的逻辑表，禁止返回旧版本路由结果冒充新版本。
5. 实现路由缓存的引用关系与级联原子失效：为每个逻辑表维护其对物理表清单、分片边界索引与路由版本的引用关系；当分片键、分片算法参数、物理表映射或分片区间变化时，受影响逻辑表的全部派生缓存及依赖它的下游聚合视图必须级联失效并在同一事务边界内原子重建，禁止出现物理表清单已更新而分片边界索引仍为旧值。
6. 实现并发控制与幂等复用：快照提交、增量提交与级联重建按提交单写者串行执行，多个只读查询可并发读取某一完整提交版本；同一提交标识重复提交只执行一次、其余等待并复用同一结果，内容不一致返回 E_CONFLICTING_REQUEST；查询不得看到逻辑表已标记新版本而其路由缓存尚未重建的中间状态。
7. 使用 SQLite 持久化快照版本、逻辑表映射、分片区间、路由缓存与意图日志，快照提交、增量提交与级联重建前先写意图记录再提交事务；进程在级联重建中途被强制终止后重启须扫描未完成意图，把路由缓存回滚到最后一个完整快照版本或将增量标记为已中止，恢复报告只包含已落盘事实。
8. 实现可复现异常注入与本地演示接口：请求参数可注入物理表映射缺失、分片区间重叠、基础版本回退、观察版本高于当前版本与重建中途中断标记五类情形，各类返回互不相同的业务码且错误体为含业务码与上下文的 JSON；提供固定本地样本的演示脚本完成一次整份快照加载、一次仅改单逻辑表分片区间的增量提交、一次版本被替换后的陈旧读裁决与一次强制终止后恢复。

执行约束：不使用 Docker 或其他容器环境；使用本地确定性样本验证，不访问未授权目标。按上述任务意图交付相应代码、测试或技术说明，记录实际验证结果。

验收：
使用固定本地样本验证路由计算、增量提交与版本替换后的陈旧读裁决及强制终止恢复结果。
