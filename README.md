当前是空白工作区，没有现存项目、代码或数据附件，需要从零实现一个面向本地资源编排场景的「依赖图增量收敛与断点恢复管线」。管线把一组资源（数据集、派生视图、导出产物）按依赖关系组织成有向无环图，每次运行由输入资源版本变化触发，沿依赖图增量重算受影响节点，未受影响节点复用上一轮已发布的版本结果。资源处理算子包含过滤、列映射、按键分组求和与连接四类，输入输出均为本地列式数组，按配置的向量批量推进。真实编排系统的难点在于：一次运行中可能多次因外部版本发布而改变依赖，增量闭包必须每次重算且不能与正在推进的阶段交错；进程在任意批边界崩溃后必须从已提交断点续算，已发布版本与断点记录要保持一致；同一运行中并发触发的新版本变化须有序排队而不是并发改写依赖图。

任务环境与准备：
安装 Python 3.11，并通过 pip 安装 numpy、flask、pytest 的固定版本。
确认工作区为空目录，创建项目根目录与题面要求的本地样本数据目录。
样本数据与运行时目录均使用本地路径，不访问外网、数据库服务或任何在线资源。

业务要求：
1. 实现资源与阶段声明模型及依赖图校验：资源含名称、版本号、行数、列名与内容摘要，阶段含标识、输入资源名列表、输出资源名、算子类型与参数；启动时须校验依赖图无环、输入资源可解析且列类型与算子要求匹配，缺失输入返回 E_MISSING_INPUT、成环返回 E_CYCLE、类型不符返回 E_TYPE_MISMATCH，非法声明不得进入推进流程。
2. 实现四类算子的确定性批量计算：过滤、列映射、按键分组求和与连接须以 NumPy 数组批量推进且单批内不产生逐行 Python 对象，输出行序按排序键与分组键的确定次序归一化；相同输入资源版本与相同参数重复计算必须产出逐值一致的输出与相同内容摘要，空输入与含空值列须有明确定义。
3. 实现基于资源版本键的阶段状态机：阶段状态取值必须为 pending、ready、running、done、failed、skipped，只有全部输入的当前已发布版本与运行开始时快照的期望版本同时齐备时才能进入 running；非法迁移须拒绝并返回 E_INVALID_TRANSITION，被 skipped 的阶段须在运行报告中给出跳过原因。
4. 实现批边界崩溃断点恢复与已发布版本一致性：每批完成须在单个 SQLite 事务中写入批次进度、阶段中间摘要、输出行数与状态迁移，事务提交后才允许读取；进程重启后须从最后已提交批次继续，中断时处于 running 的阶段回退为 pending，已提交批次的输出不得丢失也不得重复计入已发布版本，重启续算结果须与不中断运行逐值一致。
5. 实现运行期内资源版本变化的失效传播：运行期间若某输入资源被发布新版本，须从该资源沿依赖图计算失效闭包，闭包内已 done 的阶段置为 pending 在后续推进中重算，闭包外阶段保留结果；失效计算与阶段推进须在同一一致性边界内串行，不得出现某阶段既已提交重算结果又仍被列为失效，失效诊断报告须列出每个失效阶段的直接触发资源与传播路径。
6. 实现新版本变化的有序排队与版本复用：失效闭包重算期间到达的新版本变化须进入该运行的变化队列按发布序号排队，待当前失效计算提交后再处理；同一输出资源已有内容摘要与参数均相同的已发布版本时须复用该版本并在运行报告中标记复用，新版本发布须分配严格递增版本号并原子替换元数据文件，替换前旧版本保持可读。
7. 实现本地 HTTP 接口与运行报告：提供提交运行、查询运行状态与阶段事件序列、查询资源版本清单、查询依赖图与失效诊断报告、提交运行期版本变化的接口；阶段事件须按严格递增序号持久化且可重复读取，运行报告须列出每阶段状态、输出资源版本、行数摘要与内容摘要，错误统一以固定业务码在 JSON 响应中返回。
8. 提供本地确定性样本与可重复测试：样本须包含至少四个阶段、三个中间资源、一次运行期版本变化与一次批边界崩溃场景，pytest 用例须覆盖命中复用、非法状态迁移、崩溃后续算、失效闭包范围、缺失输入与成环拒绝，全部在 Windows 上离线运行且使用固定随机种子可重复。
